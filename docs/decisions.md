# Decisions

ADR-lite log: date, decision, why. Newest at the bottom.

## 2026-11-11 — Owner live view of the current shift
**Decision:** Add a live owner screen (open tables, per-waiter sales and cash held, today vs. usual, a feed of voids/takeovers/refunds/transfers) plus owner-configurable push alerts. M4 is split into M4a (live view and alerts) and M4b (history reports). M3 must write sensitive actions to the audit log in a form the feed can query. See CLAUDE.md section 6.8.
**Why:** Owners want to watch waiters and the shift as it happens, not only read reports afterwards. In waiter-led cafés the main loss is items served but never billed, and the system can flag those because every send is recorded. It is also a selling point that plain fiscal software lacks.

## 2026-11-11 — Owner app polls; no WebSocket
**Decision:** The owner app refreshes by polling (about every 2 minutes, configurable, only while the screen is visible) plus a refresh button and pull-to-refresh, and shows an "updated at" time and per-device data freshness. Counter and handheld devices keep the optional STOMP/WebSocket table updates. Alert rules run on the server when device data syncs and are delivered as push notifications, independent of the owner app being open.
**Why:** The owner is monitoring, not operating; a delay of a couple of minutes changes no decision. Data freshness is limited by device sync anyway (devices work offline), so a socket would not make it more current. Mobile browsers drop sockets when backgrounded, so a refetch path is needed regardless. Polling is simpler and cheaper to run at €25–60/venue/month. Devices on the floor still need second-level updates so two staff don't take the same table.

## 2026-11-12 — `packages/shared` for TS domain logic
**Decision:** Add `packages/shared` for TypeScript code both `apps/device` and `apps/admin` need: money and date formatting (`1.234,50 €`, `dd.MM.yyyy`), i18n resources, VAT math, ownership and cash-limit rules. It holds hand-written logic only; `packages/api-client` stays generated.
**Why:** Without a home, this code gets copied between the two apps and drifts. One package means one fix applies everywhere.

## 2026-11-12 — Shared VAT test fixtures across Java and TS
**Decision:** VAT math lives in one function per language (Java in `apps/api`, TS in `packages/shared`). Both test suites run the same cases from `packages/shared/fixtures/vat-cases.json`.
**Why:** Devices compute totals offline and the server recomputes and rejects mismatches. A one-cent disagreement between the two implementations would reject valid offline orders in a venue. Shared fixtures make any drift fail CI instead.

## 2026-11-12 — `make` is the single dev entry point
**Decision:** `make dev` starts everything for local development. Parts that are not scaffolded yet are skipped with a note naming the issue that adds them.
**Why:** `make` ships with macOS and Linux and works across the Java and Node apps without picking a JS task runner yet. It also gives one command that keeps working while M0 is built piece by piece.

## 2026-11-12 — Git branching
**Decision:** `main` is for releases and `develop` is the integration branch. Each issue gets a `feature/<issue>-<slug>` branch off `develop`, merged back through a PR.
**Why:** this keeps `main` releasable while milestones are built incrementally.

## 2026-11-12 — Native Android/iOS folders are not committed
**Decision:** `apps/device/android` and `apps/device/ios` are gitignored and generated by Expo prebuild.
**Why:** Expo's continuous native generation keeps the native projects reproducible from config, which avoids hand-edited native code drifting from `app.json`.

## 2026-11-12 — Local Postgres via Compose, localhost only, root .env
**Decision:** `infra/docker-compose.yml` runs only Postgres 16 (pinned minor, UTC, named volume, healthcheck), published on `127.0.0.1`. The Makefile passes the root `.env` with `--env-file`, and every variable has a default. Schema and roles come from Flyway, not init scripts.
**Why:** Devices talk to the API, never to the database, so the DB stays off the venue or home Wi-Fi. Compose would silently ignore a root `.env` otherwise. `make db` waits for the healthcheck so `make dev` never starts the API against a database that isn't ready.

## 2026-11-12 — Spring Boot 3.5 for the API
**Decision:** `apps/api` uses Spring Boot 3.5.x (3.5.16), springdoc-openapi 2.8, Java 21 as the compile target, and a Maven wrapper of the `only-script` type, so no wrapper jar is committed. Spring Security, JWT and WebSocket are added with the features that need them (M1 auth, M3 live tables), not in the scaffold.
**Why:** CLAUDE.md specifies Spring Boot 3.x. Boot 4 exists, but moving to it (Jakarta EE 11, Spring Framework 7, springdoc 3) is a separate decision to take before the codebase grows. Adding Security now would lock every endpoint before there is any auth to configure.

## 2026-11-13 — npm workspaces, Node 22
**Decision:** The TS projects (`apps/device`, `apps/admin`, `packages/*`, `tools/*`) are npm workspaces with one root `package-lock.json`. Node 22 is pinned in `.nvmrc` and `engines`. React is pinned to the exact version the current Expo SDK expects (19.3.0) in both apps.
**Why:** npm ships with Node, so there's nothing extra to install locally or in CI, and Expo detects npm workspaces with no custom Metro config. One React version avoids the "two copies of React" class of bugs in a hoisted install. Expo SDK 58 and Vite 8 need Node ≥ 20.19.

## 2026-11-13 — `packages/shared` ships TypeScript source
**Decision:** `@tavolina/shared` and `@tavolina/api-client` point `main` at `src/index.ts`; Vite and Metro compile them with each app. There is no separate build step.
**Why:** No watch process or stale `dist/` during development. Either package can gain a build step later without changing any import.

## 2026-11-13 — Money and date formatting libraries
**Decision:** `formatEur` is hand-written with integer math (`1.234,50 €`). Dates use `date-fns-tz` (`formatInTimeZone`) for `dd.MM.yyyy` / `HH:mm` in `Europe/Belgrade`.
**Why:** `Intl.NumberFormat` output differs between Hermes and browsers (separators, spaces), and money must print identically on receipts and in reports. `date-fns-tz` is small and maintained, and it relies only on `Intl.DateTimeFormat` time-zone support, which Hermes has on Android.

## 2026-11-13 — API client: exported spec + openapi-typescript + openapi-fetch
**Decision:** `OpenApiSpecExportTest` (`apps/api`) boots the app on Testcontainers and writes `packages/api-client/openapi.json`. `openapi-typescript` generates `src/schema.d.ts`, and `openapi-fetch` is the runtime client. Both generated files are committed; `make api-client` regenerates them and CI (#6) fails on drift.
**Why:** No running server is needed to generate the client, and the TS apps build without Java. These are types plus a ~6 kB fetch wrapper rather than generated classes, so there is less code to review and nothing heavy on the device.

## 2026-11-13 — Java formatting with Spotless + palantir-java-format, JDK 21 builds
**Decision:** Spotless runs palantir-java-format (4-space indent, matching `.editorconfig`) and checks it in `verify`. A Maven enforcer rule requires JDK 21, and the Makefile selects JDK 21 on macOS.
**Why:** palantir keeps the existing 4-space style, which google-java-format does not. It depends on javac internals and fails on JDK 27 (`NoSuchFieldError` in `JCCompilationUnit`). JDK 21 is our target anyway, so failing fast with a clear message beats a cryptic formatter error.

## 2026-11-13 — Lint and format scope
**Decision:** One root ESLint 9 flat config (typescript-eslint, react-hooks, Prettier compat) covers every TS workspace; `eslint-config-expo` is not added for now. Prettier formats code and JSON only. Markdown, `infra/` and generated files are left as written.
**Why:** One config keeps rules consistent across apps. Reflowing hand-written docs and Compose files adds noisy diffs and catches no bugs.

## 2026-11-13 — Device layout is chosen by screen size until pairing exists
**Decision:** `apps/device` shows the tablet (counter) layout when the shortest side is ≥ 600 dp, and the phone (waiter) layout otherwise. The admin PWA manifest waits for M4.
**Why:** Device kind (`COUNTER | HANDHELD`) comes from pairing in M1/M2. Until then, screen size lets both layouts run on emulators. The same rule gives the counter layout in the web build, which the Electron desktop counter will load (`npx expo export -p web` already works).

## 2026-11-13 — Keep building while the fiscal spec is missing
**Decision:** M0–M6 continue with `MockFiscalProvider`. The missing "EFS Implementation Specifications" (NUIKF, QR payload, signing, transmission, possibly rounding) blocks M7 and pilots, not the milestones before them. Target: have the spec, or a partner's SDK, by M4.
**Why:** Everything fiscal sits behind `FiscalProvider`, and VAT rounding is one function per language with shared fixtures, so a rule change later is small. The documents we have already show four things to design for now: VAT rate letters (`A`–`E`), four-decimal SEF unit prices, discounts per VAT rate, and a receipt-number format owned by the provider.

## 2026-11-13 — Fiscal receipts are issued centrally by a venue hub on the counter
**Decision:** Phones never issue fiscal receipts. When a waiter takes payment, the phone sends the order and payments over the venue LAN to the **counter**, which acts as the venue's fiscal hub: it calls `FiscalProvider.issue`, holds the single receipt sequence and the fiscal outbox, and returns the receipt for the phone to print. Requests are idempotent by client UUID. If the hub can't be reached, the order stays unpaid until a receipt is issued.
**Why:** It means one ATK registration, certificate and key per venue instead of per phone (cheaper, and a lost phone never holds a signing key), one sequence and one Z-report per venue, and it is allowed whichever way the spec decides per-device issuing. The cost: the hub is a single point of failure, and phones need venue Wi-Fi to fiscalize. With the internet down, the LAN still works, so service continues. Promoting a backup hub is deferred because the sequence must never fork.

## 2026-11-13 — The counter runs on the venue's Windows touch-screen PC (Electron)
**Decision:** The counter POS targets the Windows 10+ touch-screen PCs that cafés already use, through an **Electron** shell (`apps/desktop`) around the device app's web build. Node provides TCP and USB/serial printing, SQLite and the hub's local HTTP server. The Android tablet build stays for venues without a PC. Phones stay on Expo. Only storage, printer transport and the hub sit behind platform adapters; screens and logic are shared. Olt approved Electron as a heavy dependency.
**Why:** Owners won't replace a working PC with a tablet, and "keep your hardware" sells. Android apps don't run on Windows, and a browser can't open raw printer sockets, serve the LAN or reach USB devices. Electron is the most established option with easy Node access to all three. Tauri is lighter but less boring. An always-on, often wired PC is also a better hub than a tablet. To validate with pilots: Windows versions (Electron needs 10+), USB versus LAN printers, and how common the PC setup really is (open question 5).

## 2026-11-13 — Explore the venue's hardware fiscal printer as a fiscal provider
**Decision:** Add `HardwareFiscalPrinterProvider` as a candidate M7 path: the hub drives the venue's existing certified fiscal printer (e.g. Datecs FP-700), which does the fiscalization. Nothing is built until AI 01/2026 is confirmed to allow it with our software, the end of the hardware transition is known, and we have each model's command protocol (open question 12).
**Why:** Many venues already have a registered fiscal printer on the counter PC. Driving it could make pilots legal without the missing SEF spec or our own certification, and it fits the hub design, since issuing happens in one place.

## 2026-11-13 — Only public regulation documents go in the repo
**Decision:** `docs/regulation/` holds public ATK and Ministry publications. Vendor manuals (such as the Datecs FP-700 guide) stay out of git because the repository is public; we record the model and where to get the manual instead.
**Why:** Government publications may be shared. A vendor's copyrighted manual in a public repo is redistribution we have no right to.

## 2026-11-13 — VAT is rounded per rate total, not per line
**Decision:** `sumByRate` adds the gross of all lines per VAT rate (after discounts), then splits each rate total once with round half-up. This replaces rounding per line and summing. Five more ATK receipt examples are in `vat-cases.json`.
**Why:** Annex F, p. 81 (10% off the total) prints VAT 18% = 1.08. Rounding per rate gives 1.08, and per line gives 1.09. Every other ATK example matches both methods, so this is the only one that decides it. Rounding per line would also lose VAT on cheap items (seven 1-cent lines give no VAT). The exact rule stays `TODO(fiscal-spec)` until we have the "EFS Implementation Specifications". How subtotal discounts are split is open question 13.

## 2026-11-13 — Fake printer: one process, many printers, one job per connection
**Decision:** `tools/fake-printer` is a TypeScript workspace (`@tavolina/fake-printer`) that runs several printers in one process, each on its own TCP port (default Bar on 9100 and Kitchen on 9101), with one live page on 9180 fed by Server-Sent Events. Each TCP connection is one job, as with raw port-9100 printers. Status replies use the bit layout from the Epson ESC/POS reference. Modes `online | offline | paperOut | slow | timeout` can be switched from the page, over HTTP, or in code. Tests import `startFakePrinter` directly. It runs with `tsx` (no build step, like `packages/shared`) and draws QR codes with `qrcode`; the page loads nothing from the internet.
**Why:** One process keeps `make dev` to a single entry, and one page shows Bar and Kitchen side by side. Separate ports per printer match how venues configure LAN printers, and a separate process still works with `--web-port`. Following the Epson status bits now means the M2 drivers parse what real printers send, and the HW milestone only adds per-model quirks as new switches.
